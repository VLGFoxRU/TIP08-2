## Что такое CI и CD

**CI (Continuous Integration)** – практика автоматической проверки кода после каждого изменения. Система загружает репозиторий, устанавливает зависимости, запускает тесты и сборку, чтобы убедиться, что код не сломал проект.

**CD (Continuous Delivery / Continuous Deployment)** – следующий этап: автоматическая доставка готового артефакта (Docker-образа) до целевой среды или его развёртывание на сервере. В данной работе ограничиваемся сборкой образа.

## Полный YAML-файл pipeline

```yaml
name: CI Pipeline

on:
  push:
    branches: [ "main", "master" ]
  pull_request:
    branches: [ "main", "master" ]

jobs:
  test-and-build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.26'

      - name: Show Go version
        run: go version

      - name: Download dependencies
        run: go mod tidy
        working-directory: ./services/tasks

      - name: Run tests
        run: go test ./...
        working-directory: ./services/tasks

      - name: Build application
        run: go build ./...
        working-directory: ./services/tasks

  docker-build:
    runs-on: ubuntu-latest
    needs: test-and-build

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build Docker image
        run: docker build -t techip-tasks:${{ github.sha }} .
        working-directory: ./services/tasks
```
---

## Пояснение шагов pipeline

- Checkout repository – клонирование кода репозитория.
- Setup Go – установка Go версии 1.23.
- Show Go version – вывод версии для проверки.
- Download dependencies – загрузка зависимостей (go mod tidy).
- Run tests – запуск всех тестов в проекте (go test ./...).
- Build application – компиляция приложения (go build ./...).
- Set up Docker Buildx – подготовка Docker для сборки образов.
- Build Docker image – сборка образа с тегом, равным SHA коммита (${{ github.sha }}).

---

## Способ формирования тега образа
Тег образа = ${{ github.sha }} – уникальный идентификатор коммита. Это гарантирует, что каждый образ связан с конкретной версией кода, и позволяет легко откатиться при необходимости.

---

## Где должны храниться секреты
Секреты (токены регистра, SSH-ключи) не должны храниться в репозитории или YAML-файлах.
Они помещаются в Settings - Secrets and variables - Actions репозитория и передаются в пайплайн как переменные окружения.
Пример: ${{ secrets.REGISTRY_PASSWORD }}.
Злоумышленник, получивший доступ к коду, не увидит значений секретов.

## Ответы на контрольные вопросы

**1. Чем CI отличается от CD?**  
CI (Continuous Integration) – автоматическая проверка кода после изменений: сборка, тесты, линтинг. CD (Continuous Delivery/Deployment) – автоматическая доставка готового артефакта (образа) до целевой среды или развёртывание на сервере.

**2. Почему pipeline должен запускать тесты?**  
Тесты – быстрый способ убедиться, что изменения не сломали существующую логику. Без автоматического запуска тестов возрастает риск пропустить регрессию.

**3. Зачем нужен автоматический build?**  
Автоматическая сборка гарантирует, что код компилируется в чистом окружении, не зависящем от локальной машины разработчика. Это исключает ситуацию «у меня собирается, а в CI нет».

**4. Почему важно собирать Docker-образ в CI, а не только локально?**  
Сборка в CI обеспечивает воспроизводимость: образ создаётся из известного состояния репозитория без ручных шагов. Это исключает случайные отличия локальной среды и гарантирует, что в registry попадёт именно тот артефакт, который прошёл тесты.

**5. Что такое CI secrets?**  
Это защищённые переменные, которые хранятся в настройках репозитория (или организации) и передаются в пайплайн только во время выполнения. В них помещают токены, пароли, ключи SSH.

**6. Почему нельзя хранить токены и SSH-ключи в репозитории?**  
Репозиторий (и его история) могут быть доступны широкому кругу лиц. Открытые секреты позволяют злоумышленникам получить доступ к registry, серверу или другим системам. Безопасность требует отделения кода от учётных данных.

**7. Для чего нужен тег Docker-образа?**  
Тег однозначно связывает образ с конкретным коммитом или версией приложения. Это позволяет откатиться к нужной версии, понять, какой код запущен, и избежать перезаписи latest без возможности отладки.

**8. Что делает job docker-build?**  
Этот job выполняет сборку Docker-образа внутри CI-среды на основе Dockerfile из репозитория. Он запускается только после успешного прохождения тестов и гарантирует, что образ создаётся из проверенного кода.

**9. Почему в multi-service проекте важен working-directory?**  
В репозитории с несколькими сервисами (например, auth и tasks) команды go build, go test и docker build должны выполняться из папки конкретного сервиса, иначе Go/Python не найдут модуль, а Docker – Dockerfile. Параметр working-directory указывает CI нужный контекст.

**10. Какие риски возникают при полностью автоматическом деплое?**  
Автоматический деплой без ручного подтверждения может внедрить ошибку сразу на production. Поэтому в реальных системах обычно используют Continuous Delivery (требуется ручное утверждение) или сложные стратегии развёртывания (canary, blue-green), чтобы снизить риск.
